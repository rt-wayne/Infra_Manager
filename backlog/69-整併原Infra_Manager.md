## 待確認（整併開工前再裁示）

④ 舊歷史申請單要不要轉進 Oracle
   影響  不轉的話，查舊單要回舊系統，舊主機得一直開著
   選項 A  全部轉入（含紙本單、已刪單、附件）

     優點  不做匯入
     缺點  切換當下還在流程中的單要另外處理
   建議 A  資料量小（約 370 張），而且規則已備好

⑤ 異動申請的簽核引擎
   影響  決定 admin 能不能在畫面改流程、依分級選流程
   選項 A  沿用 Java 版的流程表引擎
     優點  有現成程式和測試，合舊系統的後台流程管理
     缺點  系統內兩套簽核規則並存
   選項 B  改寫成本專案那種程式寫死的關卡
     優點  規則只有一套
     缺點  admin 不能再改流程；S7 等於重寫
   建議 A  舊系統把流程管理當功能在用，B 會少掉功能

⑥ 後台維護畫面
   影響  舊系統管理員目前能在畫面維護使用者、流程、選項
   選項 A  為異動申請補後台（流程、表單選項、設定）
     優點  管理員的操作不退步
     缺點  多 S14 的份量；違反本專案「DB 維護」原則
   選項 B  比照本專案，一律 DB 維護
     優點  不用做畫面
     缺點  管理員要靠開發者改 DB
   建議 A（只做流程和表單選項）  這兩項舊系統常改；使用者管理沿用 DB 維護

## 六、跟第 68 項（改名 infra_manager）的關係（architect 報告第 4 節）

- 騰出名稱只能靠改名：GitHub repo 名稱不分大小寫；封存不會釋出名稱，只有改名才會。（已依 ②A 完成）

## 七、建議 C，以及為什麼不選 A、B（architect 報告第 5 節）

- 為什麼是 C：整併後只會剩本專案的一套登入、使用者與權限。換身分、改殼 jar、統一寄信這三件，A 和 C 都躲不掉，C 只做一次。Java 版最有價值的部分剛好跟這三件無關：已審過的 DDL、申請單流程的邊界處理（樂觀鎖、搶簽、補件快照）、約 284 項業務測試，以及跟使用者一起裁示過的遷移規則。
- 為什麼不選 A：A 的唯一優勢是舊 Node 的漏洞最早消失，但那可以用小修補代替；代價是做一套注定丟掉的登入、後台、Docker 部署，還要讓使用者換兩次登入方式。
- 為什麼不選 B：程式成本最高，而且容易漏掉 Java 版已經發現、修掉的舊系統問題（Java 版第 41～54 項）。B 唯一的好處是不受 Java 版設計假設牽制；但 C 只要把 Java 程式當成「要逐段審查的參考實作」，不整包複製，一樣能避開。
- C 的前提：舊 Node 系統仍是行為的最終依據。Java 版刻意跟舊系統不同的地方（admin 不能撤回、範本只有建立者能改等），搬的時候要逐條列出、讓使用者確認。

## 八、風險提示（architect 報告第 6 節）

1. Java 版 repo 改名後本機 remote 沒改就可能推錯 repo（本機已改；其他機器待確認）。
2. 殼 jar 整包讀進記憶體：50 MB 上傳乘上同時上傳的人數會吃掉殼 jar 記憶體；Java 版當初就是因為這點才改成串流轉發。
3. 搬寄信 worker 時要先修 Java 版第 111 項 ⑥（沒有開關防護），否則關掉寄信它還是會寄。
4. 測試 DB 的 RD_USER 裡現在就有 Java 版的 31 張表和測試資料（S4 種子單、wayne 帳號）。選 C 要決定沿用還是重建；DROP 前要逐表列清單給使用者確認。
5. 舊系統使用者改用工號登入，而本專案不提供自助改密碼、密碼由 DB 設定。對原本自己設密碼的人來說是看得到的退步（待確認 ⑧）。
6. 舊系統有使用者、流程、設定、表單選項的後台畫面，本專案規定一律 DB 維護。整併後舊系統的管理員會失去這些畫面（待確認 ⑥）。
7. 系統裡會有兩套簽核規則：異動申請「送審時固定候選人」，帳號申請「每次請求重算」。三個月後接手的人如果只讀其中一半，會判斷錯。PRD 要明寫兩者的差異。
8. 舊系統取號漏洞確認還在（見已裁示 ③A 的後果）。
